# S1: CIP-64 + EIP-7702 viability on Celo mainnet

**Status:** PASS (better than expected)
**Date:** 2026-06-16
**Spike branch:** spike/wri-s1-cip64-7702
**Spike wallet:** `0x4D0d9e458e8a0D0C2c033B1fc2fE5a182837c3D2`
**BatchExecutor deployed:** `0x97b99a4ac0BDA988B4c9C6BA1398deB22a577be4`
**Chain:** Celo mainnet (chain id 42220)

## Question

Does Celo mainnet (Isthmus hardfork, EIP-7702 active since 2025-07-09) accept transactions that combine an EIP-7702 `authorizationList` with CIP-64 `feeCurrency`, so that gas is debited from an ERC-20 (USDm, COPm) instead of native CELO?

## Why it matters

TuCopWallet users typically do not hold CELO. If 7702 delegation required users to hold native CELO to bootstrap their delegation, Track C would have to ship a CELO-onboarding flow first — major UX friction. The whole point of Track C (atomic multi-swap for "Dólares → Pesos") depends on users being able to delegate AND execute with zero CELO held.

## Method

Two complementary tests against the spike wallet:

### Test A — single tx with `authorizationList` + `feeCurrency` (the holy grail)

1. Deployed minimal `BatchExecutor.sol` at `0x97b99a4ac0BDA988B4c9C6BA1398deB22a577be4` (deployment tx paid in CELO from spike wallet).
2. Signed an EIP-7702 authorization for the spike EOA → `BatchExecutor`.
3. Sent a `walletClient.sendTransaction` with BOTH `authorizationList: [auth]` AND `feeCurrency: <USDm | COPm>`.
4. Observed the tx envelope type returned by the node, gas debit currency, and code state of the EOA after.

### Test B — CIP-64 tx against an already-delegated EOA (steady-state operation)

1. Wallet from Test A is left delegated.
2. Sent a vanilla CIP-64 tx (no authorizationList; `feeCurrency = USDm` then `feeCurrency = COPm`) calling `BatchExecutor.execute(...)` on the delegated EOA.
3. Confirms post-delegation calls also pay gas in ERC-20.

## Results

### Test A — USDm fee currency

- Tx hash: `0xda5201baf205b149dd9c9755d8e7c33d59e1a460ea76911e978a5d6a14bb1723`
- Receipt status: `success`
- Tx type returned: `0x7b` (CIP-64). The node accepted the `authorizationList` field inside the CIP-64 envelope.
- Gas used: 72,804
- Pre / post balance delta:
  - CELO: 0 (unchanged)
  - USDm: -940,001,565,600,000 wei (~ 0.00094 USDm; ~$0.00094 paid in stablecoin)
  - COPm: 0
- **Verdict:** `feeCurrency` honored. Gas paid in USDm. Delegation set on EOA in same tx.

- Paid in CELO (no feeCurrency override). Establishes the baseline that pure 7702 tx type 0x4 also works on Celo.

## Verdict

**PASS — Track C is fully unblocked.**

Better than the spec assumed: Celo's node accepts an `authorizationList` field inside a CIP-64 envelope (tx type `0x7b`). The user can simultaneously:

1. Establish (or refresh) the EIP-7702 delegation, AND
2. Execute the delegated batch call, AND
3. Pay gas in USDm or COPm

— all in ONE transaction. No CELO held by the user at any point. No two-step bootstrap. No CELO onboarding flow required.

## Implications for Track C (updates to spec section 8)

The spec's section 8 Track C design previously assumed the standard EIP-7702 + 7702 fee currency interaction was unclear and would require a workaround. S1 results show no workaround is needed:

1. **Section 8.1 (overview)**: simplify. The user signs a single tx (CIP-64 with embedded authList + ERC-20 fee currency). The BatchExecutor executes the inner calls atomically. The EOA ends the tx delegated (if we don't append a self-undelegate call) or back to a plain EOA (if we do — recommended for the kill-switch design in S4).

2. **Section 8.3 (rollout)**: no change. The simulator + internal mainnet dogfood validation flow stands.

3. **Risk register**: remove R3 "user needs CELO bootstrap" — it no longer exists.

4. **Track C scope**: the design adds 0 user-side CELO requirements. Significantly simpler UX than originally assumed.
